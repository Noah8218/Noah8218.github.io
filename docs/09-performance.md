# 09. 성능: 측정, 원인, 조치, 남은 한계

이 문서의 수치는 **2026-11-27에 한 대의 Windows PC에서 Edge(Chromium) 헤드리스로 잰 값**이다. 측정 원자료(JSON·텍스트)는 저장소 밖에 있고, 이 저장소에는 도구만 있다. 다시 재려면 `tools/perf_site.py` 등을 쓴다(6절). 코드가 바뀌었으면 수치도 달라진다.

## 1. 이 문서가 답하는 질문

질문: **"이 사이트가 버벅이는가? 무엇이 원인이었고, 무엇을 고쳤고, 무엇이 남았는가?"**

결론: 측정한 조건(Windows PC 한 대, Edge 헤드리스, `file://`)에서 개선 전의 가장 큰 비용은 히어로 캔버스였다. 맨 위에 가만히 있어도 메인 스레드를 21.6~23.2% 썼고(CPU 4배 스로틀에서 53~90%), 테마를 바꾸면 스로틀 없이 66~121ms, 4배 스로틀에서 267~763ms가 걸렸다. 히어로 캔버스, 테마 전환, 등장 전환, 미디어 재생 시작 시점을 고친 뒤 유휴 점유는 3.7~4.7%(4배 스로틀 13~22%), 테마 전환은 스로틀 없이 17~40ms가 됐다(3절). 스크롤 프레임 끊김은 회차마다 변동이 커서 개선을 단정하지 못한다(스로틀 없는 데스크톱의 50ms 초과 프레임은 전 4~5개, 후 1~3개였으나, 이식한 도구로 다시 잰 2회는 6개였다. 3-7절). 개선되지 않은 것도 있다: (1) 로드 직후 긴 작업(레이아웃)은 줄지 않았고 4배 스로틀에서는 최장 약 0.9~1.7초가 반복된다, (2) 첫 언어 전환은 4배 스로틀에서 약 1.0~1.5초다, (3) 느린 기기에서 GIF·mp4 행의 재생 CPU 점유(약 24~52%)는 그대로다, (4) 4배 스로틀 케이스의 스크롤 끊김은 같은 코드 재측정(base2)과 차이를 확인하지 못했다. **모든 기기에서 매끄럽다고 말할 근거는 없다.** Safari, Firefox, 실제 터치 기기, 실제 네트워크(압축·캐시·지연)는 **측정하지 않았다.**

## 2. 측정 방법

| 도구 | 하는 일 | 출력(기본 `tools/out/`, `--out`으로 변경) |
|---|---|---|
| `tools/perf_site.py` | 한 케이스를 1회 측정: 로드(DCL, load, FCP, LCP, CLS, 긴 작업), 유휴 CPU 5초, 전체 스크롤 프레임 시간(전체·섹션별), 미디어 행 4개 5초 점유, 테마·언어·썸네일 전환 반응 시간 | `perf_<케이스>_<gpu>.json` |
| `tools/perf_profile.py` | 로드·유휴 구간 CPU 프로파일(자기 시간 상위 함수)과 로컬 http 서버에서의 전송량 | `perf_profile_cpu<배수>.txt` |
| `tools/perf_ab.py` | 스크롤 끊김 원인 분리: 캔버스·블러를 하나씩 꺼서 base/noblur/nocanvas/none을 2회씩 비교 | `ab_cpu<배수>.json` |

| 케이스 | 뷰포트 | CPU 스로틀 | 가정 |
|---|---|---|---|
| `desktop` | 1440x900 | 없음 | 일반 데스크톱 |
| `desktop_slow` | 1440x900 | 4배(`Emulation.setCPUThrottlingRate`) | 느린 노트북 |
| `mobile_slow` | 390x844 모바일 에뮬레이션 | 4배 | 느린 휴대폰 |

**한계와 잡음**

- `file://`로 열어서 **네트워크 지연·압축·캐시가 들어가지 않는다.** 전송량은 `perf_profile.py`가 로컬 http 서버(표준 라이브러리, 압축 없음)로 따로 잰다.
- **헤드리스라 실제 화면 합성(GPU)과 다르다.** 측정 PC의 주사율이 약 120Hz(프레임 시간 p50 8.3ms)라 fps 절댓값이 60Hz 기기와 다르다. 값은 같은 PC의 전후 비교로만 읽는다.
- **측정 잡음**: 다른 작업이 겹치면 한 번에 500~650ms가 튄다(예: 기준선 A/B 4배 스로틀 base 2회차 최대 프레임 650ms, 개선 후 A/B base 1회차 608ms). 그래서 같은 케이스를 2회 이상 재고, 원인 분리는 A/B로 확인했다. 최대 프레임 시간은 잡음에 좌우돼 3절 표에서 뺐다.
- 힙(9.5MB)과 DOM 노드 수(864)는 전후 같았다. CLS는 전 6회가 모두 0이고, 후는 15회 중 최대 0.002였다(0~0.002).

**어떤 코드를 쟀는가** (JSON의 `files` 키 = 파일별 SHA-256 앞 12자리)

| 구분 | index.html | css/style.css | js/main.js | js/hero.js |
|---|---|---|---|---|
| 전(base2) | 8eba16694c5e | 1fddcb5c1843 | 48a28bca463d | 62c742347c29 |
| 후(me_final, after_final) | 8406e4dccb21 | 204316688f91 | 640e11ed8b13 | 40a852aa6dd3 |

base2의 해시는 성능 작업 직전 코드(작업 전 백업)와 일치하고, 후의 해시는 이 문서를 쓴 시점의 현재 코드와 일치한다. 최초 기준선 `base`는 `css/style.css` 해시가 달라서(A 구역 수정이 진행 중이던 시점으로 보인다) 참고용이다.

## 3. 전/후 비교

표기: 칸의 `a / b`는 회차별 값이다. 열 이름은 원자료 파일 묶음 이름이다(표 아래에 파일명). `me_final`은 개선 후 최종 2회, `after_final`은 같은 코드의 추가 3회다.

**주의(desktop 케이스의 `me_final`)**: `me_final_desktop` 2회는 유휴 CPU 0.1·0.2%, LCP와 FCP가 같음(644·724ms), 문서 높이 14959·15291px이다. 같은 코드의 `after_final_desktop` 3회(유휴 3.7~4.7%, 문서 높이 17842~18120px)와 다르고, 문서 높이는 [03 문서](03-site-architecture.md) 8절에 적힌 "정지 모드 약 15,000px"에 가깝다. **모션 정지(`html.still`) 상태로 측정됐을 가능성이 크다(추정, 원인 미확인).** 정지 상태에서는 히어로 캔버스가 멈추므로 이 두 회차의 desktop 유휴 CPU·LCP·테마 전환 값은 개선 효과의 근거로 쓰지 않는다. 그래서 desktop 개선 효과는 `after_final`로 읽는다. `perf_site.py`는 이 상태를 알아보도록 JSON에 `motion_still`을 남긴다.

### 3-4. 표를 읽는 방법과 판단

| 지표 | 판단 | 근거 |
|---|---|---|
| 유휴 CPU | **개선**. 세 케이스 모두 base2보다 약 2.4~6.9배 낮다 | desktop 21.6 → 3.7~4.7, desktop_slow 81.7~89.6 → 12.9~15.7, mobile_slow 53.2~53.5 → 13.0~21.9 |
| 테마 전환 | **개선** | desktop 66~121 → 17~40ms, desktop_slow 267~763 → 97~211ms, mobile_slow 394~727 → 29~254ms |
| LCP | **개선, 변동 큼**. LCP 요소는 모든 측정에서 히어로의 `p.tag.reveal`이다 | desktop 2084~2132 → 936~1416, desktop_slow 3452~3580 → 2000~2736, mobile_slow 3512~3564 → 1608~3576(후 5회 중 한 번은 전과 같은 3576) |
| 스크롤 끊김 | **개선을 단정하지 못함**. desktop은 줄어든 회차가 있으나 재측정(3-7)에서 다시 늘었고, 느린 두 케이스는 base2와 차이를 확인하지 못함 | desktop 50ms 초과 프레임 4~5개 → 1~3개(after_final), 이식 도구 재실행 6 / 6. desktop_slow는 5~6개 → 3~14개, mobile_slow는 5~6개 → 3~31개로 범위가 겹치거나 더 넓다 |
| 로드 긴 작업 | **개선 없음** | desktop 최장 293~294ms → 0~297ms. 4배 스로틀 후 10회 중 8회에서 최장 0.88~1.68초(전에도 0.11~1.48초) |
| 첫 언어 전환 | 4배 스로틀에서 **다소 줄었으나(중앙값 기준 약 20~25%) 여전히 느림**, desktop은 일관성 없음 | desktop_slow 1771~1846 → 990~1521ms, mobile_slow 1533~1987 → 458~1431ms. desktop은 271~338 → 16~262ms |
| 미디어 행 점유 | **변화 없음** | 4배 스로틀 4행 범위 전 25.3~48.3% / 후 23.8~51.9% |

`base`(1회)는 스크롤 끊김 수치가 base2보다 나쁘다(desktop_slow 50ms 초과 22개 대 5~6개). 같은 코드가 아니고 잡음도 있어서 전후 비교는 base2를 기준으로 한다.

읽은 파일: 전 CPU 1배 = `base_ab_cpu1.json`, 전 CPU 4배 = `ab_cpu4.json`(`base_ab_cpu4.json`과 같은 내용), 후 CPU 1배 = `after_ab_cpu1.json`(`ab_cpu1.json`과 같은 내용). 후 CPU 4배 A/B는 없다.

- 전: 캔버스·블러를 꺼도(none) 50ms 초과 프레임이 줄지 않았다. 가장 나쁜 프레임의 스크롤 위치는 모드와 무관하게 같은 곳(Y 1680·1800·4320px 부근)에서 반복됐다(예: base 142·108·92ms). **캔버스와 블러는 스크롤 끊김의 주원인이 아니었다.** 캔버스는 히어로가 화면 안일 때만 그리기 때문이다(코드: `IntersectionObserver`).
- 후(CPU 1배): base 50ms 초과가 3·2개로 줄었고 p99는 25 → 16.7ms다. 같은 위치(Y 1680·4400px 부근)가 여전히 가장 나쁘지만 50~100ms로 낮아졌다(1회차의 608ms는 Y 600에서 한 번 튄 값이라 잡음으로 본다). **그 위치에 무엇이 있는지, 어느 변경이 줄였는지는 변경별로 분리해 확인하지 않았다(추정: 미디어 행 진입 시 GIF·영상 시작과 이미지 디코드).**

- 로드 시점 용량은 4KB 늘었다(히어로 JS·CSS 증가). 끝까지 스크롤한 뒤 용량이 줄어든 것은 GIF 3개와 mp4 1개(요청 4개)가 더는 받아지지 않았기 때문이다. **이 스크롤은 120px씩 약 30ms 간격으로 빠르게 지나간 것이라, 행에 머무르면 그 행의 GIF·mp4는 그때 받는다.** 즉 5691 → 2020KB는 "스크롤로 지나가기만 할 때"의 값이다.
- 전 전송량 5691KB 중 GIF는 2331KB(약 41%), 가장 큰 단일 파일은 `ovl-tool-settings.mp4` 1343KB였다.
- 로드 구간에서 (idle)을 뺀 CPU 표본은 3913ms → 1821ms(두 텍스트 파일의 값으로 계산)로 줄었다. 반면 `layoutEco`의 자기 시간은 66.9ms → 1062.7ms로 커졌다. 전에는 같은 레이아웃 비용이 `(program)`(브라우저 내부 시간)에 섞여 있었고, 지금은 `layoutEco`의 첫 `offsetWidth` 읽기가 문서 전체 레이아웃을 한꺼번에 치르는 것으로 **보인다(추정, 호출 그래프로 확인하지 않음).** 5절의 "로드 직후 긴 작업"이 이것이다.
- 테마 전환 프로파일(`base2_themeprof_x1.txt`, 전 코드, 스로틀 없음): 첫 전환 89ms, 작업 96.8ms 중 스타일 재계산 56.1ms, `getPropertyValue` 자기 시간 61.0ms. 언어 전환 프로파일(`base2_langprof_x1.txt`, 전 코드, 스로틀 없음): 첫 전환 270ms, 작업 405.6ms 중 레이아웃 213.2ms, `layoutEco` 자기 시간 231.3ms. 두 프로파일 모두 개선 후에는 다시 뜨지 않았다.

## 6. 재측정 방법

저장소 루트에서 실행한다. 도구는 Edge 또는 Chrome이 필요하고, 못 찾으면 환경 변수 `BROWSER`에 실행 파일 경로를 준다([tools/README.md](../tools/README.md)). **이 저장소의 `perf_site.py`는 `--case desktop`을 2회 전체 실행해 JSON이 생기는 것을 확인했다(3-7절). `perf_profile.py`와 `perf_ab.py`는 `py_compile`과 `--help`만 확인했고 브라우저를 띄우는 전체 실행은 하지 않았다.** 3절의 수치는 같은 측정 로직의 원본 스크립트로 잰 것이다.

```
python tools/perf_site.py --case desktop        # 케이스당 약 1분. desktop_slow, mobile_slow 도 같은 방식
python tools/perf_site.py --case desktop_slow
python tools/perf_site.py --case mobile_slow
python tools/perf_profile.py --cpu 4            # CPU 프로파일 + 전송량(텍스트)
python tools/perf_ab.py 1                       # 스크롤 끊김 원인 분리 A/B (4 를 주면 CPU 4배)
```

절차:

1. **코드를 크게 바꾼 뒤에만, 다른 작업을 모두 끄고** 잰다(브라우저 탭, 빌드, 영상 재생, 다른 측정 포함). 겹치면 500~650ms가 튄다. 새 프로필 폴더(`tools/.browser-profile-perf-*`)의 **첫 실행은 로드가 15초까지 느려진 적이 있으니(3-7절) 버리고 한 번 더 잰다.**
2. 같은 케이스를 2회 이상 잰다. 결과는 `tools/out/`에 쌓인다(`.gitignore` 대상). `--out`으로 이름을 달리해 덮어쓰기를 피한다.
3. JSON에서 `motion_still`이 `false`인지 먼저 본다. `true`면 모션 정지 상태라 비교할 수 없다(프로필 폴더가 실행 사이에 남아 저장된 설정이 이어질 수 있다. 3절 desktop 주의 참고).
4. `files` 해시로 어떤 코드를 쟀는지 확인한다.
5. 비교는 이 문서 3절의 base2·after_final 값과 한다. 이전 코드를 재려면 이전 커밋을 별도 폴더에 받아 그 폴더의 `tools/`로 같은 명령을 실행한다(도구는 자기 위치의 부모 폴더를 사이트로 본다).

주로 볼 JSON 키: `load.lcp`, `load.longtasks`, `idle_top_5s.main_thread_busy_pct`, `scroll_all`(`avg_fps`, `p99`, `over_50`), `interaction.theme_toggle_ms`·`lang_toggle_ms`, `media_rows_5s`.

## 7. 이 사이트에서 성능을 해치므로 다시 넣지 말 것

근거는 4절·3절의 diff와 측정이다. 새로 넣어야 한다면 먼저 사용자에게 묻고([AGENTS.md](../AGENTS.md) 2절), 넣은 뒤 6절로 재측정한다.

- **전체 해상도 캔버스를 매 프레임 지우고 점 격자를 전부 다시 그리는 히어로.** 전에는 유휴 점유가 21.6~23.2%(4배 스로틀 81.7~89.6%)였다. 정적 부분은 오프스크린 캔버스에 한 번 그려 복사하고, 프레임은 약 30fps로 제한하고, 화면 밖·탭 숨김·정지 모드에서 멈춘다.
- **점마다 포인터 거리를 계산하는 밀어내기 효과.** 제거한 코드(4절). 이 효과의 단독 비용은 분리해 측정하지 못했다.
- **스크롤 중 행이 보이자마자 GIF·영상을 시작하는 것.** 끝까지 빠르게 스크롤했을 때 5691KB(gif 2331, mp4 1343)를 받았다. 지금은 행에 300ms 머물고 스크롤이 150ms 멈춘 뒤에만 시작한다.
- **GIF를 디코드하지 않은 채 `src`로 바로 교체하는 것.** `decode()`가 끝난 뒤 교체한다. 새 `<img>`에는 `loading="lazy" decoding="async"`를 붙인다(기존 행을 복제하면 따라온다).
- **테마 전환 중 모든 요소에 색 전환을 거는 것(`html.tm`).** 전환이 스로틀 없이 66~121ms였고 스타일 재계산 56.1ms가 보였다. `html.nt`로 전환을 끈다.
- **클릭 핸들러 안에서 `getComputedStyle`·`getPropertyValue`를 읽는 것**(테마 전환 때 히어로가 그랬다). 스타일 재계산이 강제된다(`getPropertyValue` 61.0ms). 읽기는 다음 프레임으로 미룬다.
- **DOM 읽기(`offsetLeft` 등)와 쓰기(`setAttribute`)를 노드마다 번갈아 하는 코드.** 구성도 `layoutEco()`가 그랬다(자기 시간 231.3ms). 읽기를 먼저 모두 끝낸다. 단, 개선 후 효과는 다시 프로파일하지 않았다.
- **크기 변경(`ResizeObserver`)마다 즉시 큰 캔버스를 다시 만드는 것.** 150ms 디바운스한다.

**근거가 없어 이 목록에 넣지 않은 것**: 내비 `.pill`과 모바일 메뉴의 `backdrop-filter`(작은 영역). A/B(3-5)에서 끄기 전후 차이가 없었다. 큰 영역에 새로 쓰는 경우의 비용은 측정하지 않았으므로, 넣는다면 `perf_ab.py`로 확인한다. 등장 블러(`.reveal`의 `filter`)는 성능이 아니라 디자인 금지(AGENTS.md 2절)다.
